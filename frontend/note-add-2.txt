AmpWise — Backend Handoff: Remaining V2 Requirements
=====================================================

This file lists only unresolved backend capabilities or verification blockers.
Existing v0.5 routes connected in the frontend are tracked in `note-add.txt`.

1. Persistent action status
---------------------------

Problem:
The frontend has an adapter for status updates, but the backend has no
`PATCH /api/actions/{action_id}/status` route. Action state is therefore local
only and persistent controls remain disabled in API mode.

Affected route: `/actions`
Endpoint: `PATCH /api/actions/{action_id}/status`
Required body: `{ "state": "assigned" | "done" }`
Expected response: updated v0.5 `Action`, including `id`, `state`, rank, issue
fields, report fields and financial fields.
Priority: Required for persistent operations; optional for a read-only demo.

Acceptance criteria:
- Valid action IDs can be updated.
- Unknown IDs return the contract `not_found` error.
- Later `GET /api/actions` calls return the updated state.
- Persistence behavior is documented for the no-login deployment.

2. Station-to-charger discovery
-------------------------------

Problem:
The frontend must not derive charger IDs from `n_chargers`, but no backend
route lists chargers for a station.

Affected routes: `/map`, `/stations/:id`, `/chargers/:id`, `/what-if`
Proposed endpoint: `GET /api/stations/{station_id}/chargers`
Required path parameter: `station_id`
Proposed response:

```json
[
  { "charger_id": "stn_001_c1", "station_id": "stn_001", "power_kw": 7.1, "status": "healthy" }
]
```

Priority: Required before enabling charger selection for arbitrary API stations.

Acceptance criteria:
- Every returned charger belongs to the requested station.
- Every returned ID is accepted by the charger-health endpoint.
- Stations without a discoverable charger list return `[]`, not guessed IDs.

3. Sessions and network uptime
------------------------------

Problem:
The backend exposes no session or uptime route. Overview and Sessions cannot
claim live session counts, energy or uptime.

Affected routes: `/` and `/sessions`
Proposed endpoints:
- `GET /api/sessions?start=&end=`
- `GET /api/network/status?time=`

Proposed response fields:
- Sessions: stable session ID, station ID, start/end timestamps and validated
  energy or power fields.
- Network status: online stations, total stations and uptime percentage.

Priority: Required only if live Sessions and uptime are part of the demo.

Acceptance criteria:
- Values are derived from approved ACN data or explicitly unavailable.
- California station-local timestamps and USD metadata are preserved.

5. What-if scenario support
----------------------------

Problem:
The backend currently rejects `discount`, although the v0.5 request enum lists
it. The frontend correctly sends only supported fields and surfaces the API
error instead of fabricating a result.

Affected route: `/what-if`
Endpoint: `POST /api/whatif`
Required decision: implement `discount` or explicitly remove it from the
supported backend enum. Delayed repair still needs an approved repair-time
field if required for the demo.

Priority: Required only for those scenarios to be demonstrated.

Acceptance criteria:
- Supported scenarios return deterministic before/after values from existing
  model inputs.
- Unsupported scenarios return the documented `bad_request` response.

6. Backtest week registry

not use the `week` value and Meta does not publish supported week identifiers.

Affected route: `/results`

Resolved during time synchronization audit
-------------------------------------------

- The repeated 400s were caused by requests starting before frontend metadata
  initialization and by the explicit legacy `MOCK=1` backend fallback returning
  2026 Malaysia/RM metadata.
- Time-dependent frontend queries are now gated on one metadata-backed time
  source, and HTTP 400 responses are not automatically retried.
- Backend default configuration now selects `MOCK=0`, which reads the existing
  California dataset. No ML data or model artifact was changed.
- Re-verify live `/api/meta`, `/api/stations` and `/api/actions` after the
  backend environment has `pydantic_settings` installed and FastAPI is running.

Overview data gaps confirmed
----------------------------

- `/api/stations` supports current station and charger availability only; it
  does not provide delivered energy, live sessions, historical uptime or
  station-session totals.
- `/api/actions` supports operational alerts but does not provide a separate
  notification timestamp/event stream. The frontend therefore preserves rank
  and state rather than inventing a latest timestamp.
- Required proposals remain the sessions/uptime endpoints described above if
  those Overview metrics must be live rather than unavailable.

Temporary Overview endpoint
---------------------------

Status: **BACKEND PLACEHOLDER — REPLACE WITH REAL IMPLEMENTATION**

Problem:
The Overview needs energy delivered, weekly energy, live sessions, historical
uptime and an energy trend, but the current backend exposes no approved session
or uptime source.

Endpoint:
`GET /api/overview`

Response:
`data_source`, `energy_delivered_kwh`, `energy_delivered_week_kwh`,
`live_sessions`, `network_uptime_pct`, and `energy_trend[]` with `date` and

`backend/app/utils/placeholder_data.py`, validated by

Frontend impact:

`frontend/src/features/overview/hooks/useOverview.ts`. The UI shows a small
backend placeholder indicator.

Required replacement:
Build an approved California/US aggregation service from real session and
network-health data. Do not estimate kWh from charger power, estimate live
sessions from charger counts, or derive historical uptime from current
availability.

Priority: Required before presenting these Overview metrics as live data.

Acceptance criteria:
- The response shape remains compatible.
- `data_source` changes from `placeholder` to the agreed real-data value.
- Energy trend dates are within the active California dataset range.
- Uptime is historical and documented; live sessions are backed by real
  session records.
- The placeholder fixture can be removed without changing frontend components.

Predicted waiting-time status
-----------------------------

Verified behavior:
- `/api/stations?time=2020-02-25T07:00:00-08:00` returns station-specific
  `predicted_wait_min` values: `0.0`, `0.0`, `0.0` and `120.0` for the four
  California stations.
- `/api/stations/{station_id}/forecast?start=2020-02-25T07:00:00-08:00&hours=24`
  returns 48 station-specific slots. Some stations have future non-zero slots,
  while the current slot can legitimately be zero under low demand.
- The queueing service uses the existing M/M/c calculation and caps unstable
  queues at 120 minutes. No frontend or backend fixture was used to inflate
  waiting times.

Frontend status:
- Map cards, KPI averages, station detail popup and station forecast mapping
  now preserve valid zero values and show `Prediction unavailable` only for
  missing or invalid values.
- The selected-station popup now requests the API forecast instead of relying
  on the map list's empty forecast preview.

Remaining backend clarification:
